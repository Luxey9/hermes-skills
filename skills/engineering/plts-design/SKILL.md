# Desain PLTS (Off-Grid/Hybrid) untuk User

## Alur kerja

1. **Kumpulkan beban dulu** — daftar alat (W × jam/hari), hitung Wh/hari dan beban puncak bersamaan. Beban motor (kulkas/pompa) surge 2–3× daya nominal → tentukan rating inverter dari surge, bukan running.
2. **Hitung dengan execute_code/Python, jangan mental** (instruksi wajib untuk aritmetika):
   - Panel Wp = Wh_hari / (peak_sun_hour × 0.8). Peak Sun Hour Indonesia ±4.2–5.0.
   - Baterai Wh = Wh_hari / (DoD × ef_inverter 0.9). Naikkan ke ukuran pasaran.
   - Pilih tegangan sistem dari skala: <1 kWh/hari → 12V; 1–3 kWh → 24V; >3 kWh → 48V.
   - MPPT ≈ Wp / V_sistem + margin — contoh: 800Wp @ 24V → ~33A → pakai 50A.
3. **Susun seri/paralel**: panel seri menaikkan Voc (cek tetap di bawah max input MPPT, biasanya 100V), paralel menaikkan arus. Baterai 12V diseri untuk mencapai 24V/48V.
4. **Pilih komponen pasaran**: panel monocrystalline 200–410Wp (merek lokal: JSI, PHC, Sunecosolar), MPPT Victron SmartSolar/EPEver Tracer, LiFePO4 12V 100Ah, inverter pure sine 24V. Rincian & tabel keputusan di `references/komponen-standar.md`.
5. **Simulasi: pakai simulator sendiri dulu** — repo `plts-simulator` (Vite+React+TS+@xyflow/react+zustand) di `C:\Users\MyBook Hype AMD\Documents\File Faqod\Program\plts-simulator\`: canvas drag-drop (panel/MPPT/baterai/inverter/beban/breaker/fuse), Wizard kebutuhan→BOM→Build di Canvas, Timeline playback multi-hari, Report RAB, katalog 87 item pasar Indonesia. Jalankan: `npm test` (vitest) dan `npm run dev` (localhost:5173), commit lokal tanpa push. Roadmap user: katalog terlengkap ala SolarBuilder + mode on-grid (net metering, tagihan PLN, payback). Prioritas yang user tetapkan untuk alur kalkulator → simulasi → laporan: **samakan dulu UI/UX editor dengan SolarBuilder (spec visual di `references/solarbuilder-ui.md`) baru kalkulasi/laporan** — bantu kembangkan repo ini, jangan lengah ke alat luar. Desain SolarBuilder bisa dikirim sebagai **file JSON ekspor** (skema + nama terminal + simSettings di `references/solarbuilder-design-json.md`) — itu sumber data mentah, bukan sekadar gambar. Selama fase paritas UI, situsnya **boleh di-harvest langsung** (CSS + DOM live + ikon PNG); prosedur & jebakannya di skill `clone-web-ui`.
6. **Alat web eksternal hanya sebagai pembanding**: Solar Builder (solarbuilder.net, berat di browser — user buka sendiri), PVAlign, guru.technosains.com (kalkulator Indonesia). Yield per lokasi pakai PVGIS — resep API di `references/pvgis-api.md`.
7. **Deliverable**: tabel komponen + diagram koneksi teks + rating fuse/kabel; kalau lewat simulator sendiri, lampirkan hasil sim (SOC timeline, unmet load). User merangkai sendiri di simulator — berikan instruksi klik, jangan coba buka sendiri kecuali via repo sendiri.

## Rangkaian seri/paralel (engine + kanvas)

- **`src/engine/array.ts` = sumber kebenaran topologi listrik**, bukan `solve.ts`. API: `arrayTopology(graph)` (-> `strings`, `seriesPerString`, `parallelStrings`, `arrayVoc`, `arrayVmp`, `arrayImp`, `dangling`, `stringMismatch`) dan `batteryBank(graph)` (-> `seriesCount`, `parallelCount`, `nominalV`, `capacityWh`, `internalResOhm`, `maxChargeAmps`). `solve.ts` wajib memfilter SEMUA `solarPanel` (bukan `findFirst`) lalu memakai hasil ini.
- **`seriesParallel(graph, units)` = SATU mesin rantai untuk semua tipe komponen**, plus `parallelUnitCount(graph, type)`. `panelStrings()` dan `batteryBank()` dua-duanya memanggil mesin ini — jangan menulis penelusur rantai kedua per tipe, dan jangan mengunci pemeriksa tipe di dalamnya (`seriesSuccessors` menerima himpunan id unit, bukan literal `'solarPanel'`; logika yang disalin dua kali akan menyimpang).
- **Polaritas dibaca dari NAMA port**, bukan urutan gambar: `terminalRole()` mencocokkan pola `pv_pos`/`bat_neg`/`dc_pos`/`ac_line`. Untuk terminal huruf (`a`,`b`) jatuh ke urutan skema: indeks 0 = `+`, 1 = `-`. Index tetangga terminal disimpan ber-prefix (`p1:a`) — kalau terminal polos dicari tanpa prefix, rantai seri putus dan dua string sejajar ikut terjumlah tegangannya.
- **Aturan rangkaian**: `+` modul ke `-` modul berikutnya = SERI (tegangan dijumlah, arus dibatasi modul terlemah); kutub sama ke kutub sama (`+` ke `+`, `-` ke `-`) = PARALEL (tegangan tetap, arus dijumlah). Bank baterai: seri menaikkan tegangan, paralel menaikkan kapasitas; R internal = (R unit x seri) / paralel.
- **Perangkat tanpa rangkaian seri** (MPPT, inverter) memakai `parallelUnitCount`: hanya unit yang benar-benar berkabel yang menambah kapasitas, unit menganggur tidak dihitung. Di `solve.ts`, MPPT paralel menjumlah `maxA` (batas Voc pakai `maxInputV` TERKECIL antar unit) dan inverter paralel menjumlah `ratedAcW` + rating `surgeW` (ambang shutdown pakai `minDcV` TERBESAR).
- **Rugi konversi MPPT sekarang dipakai**: `mpptEfficiency()` — default **0,97** bila `eff` kosong (dulu diabaikan total sehingga keluaran = panel x 1,0), nilai > 1 dianggap persen, dirata-rata untuk unit paralel. Urutannya penting: **batas arus dulu** `min(panelW, Vbat x maxA)`, baru dikali eff.
- **State = PORSI UNIT, bukan angka grup — unit ke-2 dan seterusnya DILARANG diberi entri nol.** Dulu tiap grup hanya mengisi state unit PERTAMA (sisanya `power: 0`/`current: 0`, baterai bahkan tanpa `soc`), sehingga kartu unit ke-2 tampak mati: STATE "—", bar SOC kosong, "0.00 A · 0 W" — dilaporkan pemakai sebagai "baterai kedua tidak menampilkan tegangan". Kontraknya sekarang: `ComponentState.group` (`GroupInfo`: kind/seriesCount/parallelCount + V/I/W grup) diisi untuk SEMUA unit, dan angka unit mengikuti aturan seri/paralel — seri membagi tegangan (V unit = V grup / seri), paralel membagi arus (I unit = I grup / paralel), `soc` satu bank sama untuk semua unitnya. Kartu panel = kartu MODUL (Vmp modul + arus string), jadi V x A kartu = daya grup / jumlah modul dan jumlah seluruh kartu = daya grup; angka grup hanya muncul di baris spek BANK/ARRAY/PARALEL (`groupRows` di `src/components/nodes/groupRow.ts`, disembunyikan untuk grup satu unit). Kalau mengubah pembagian ini, jaga identitas `power == voltage * current` per kartu — kecuali inverter yang memang V_dc x I_dc = P_ac / eff.
- **Jangan membaca `states.find(unit)` untuk nilai tingkat GRUP.** `simulate.ts` dulu mengambil produksi PV dari state panel pertama; begitu kartu panel jadi per-modul, timeline under-report sebesar jumlah modul. Produksi grup diambil dari `out.totalProductionW` (nilainya = `panelW`, sama persis) — nilai agregat itu urusan `solve()`/`summarizeArray()`, bukan urusan satu state.
- **`wireDrops[].from` berisi id TERMINAL (`b1:a`), bukan id node** — `worstDropPct` yang mencari `d.from` langsung ke peta state selalu meleset sehingga vDrop% selamanya 0%. Buang akhiran port dulu (`split(':')[0]`), dan acuan tegangannya `group.voltage` (tegangan bank), bukan tegangan unit. Fixture uji lama lolos hanya karena memakai `from: 'p1'` — bentuk yang tidak pernah dihasilkan solver; saat menguji ringkasan, salin bentuk asli dari `solve()`.
- **Info konfigurasi jangan ditumpangkan ke `warnings`** — badge warning di kartu itu untuk FAULT. "Bank 4S1P @ 51.2V" dulu menyalakan badge padahal rangkaiannya sehat; sekarang jadi baris spek.
- **FIX sebenarnya untuk "tidak bisa connect": tiap port merender SEPASANG handle (`target` + `source`) di posisi identik.** `BaseNode` dulu menetapkan tipe handle dari SISI kartu (kiri/atas = `target`, kanan/bawah = `source`), jadi `bat_pos`/`bat_neg` (port di sisi atas) dua-duanya `target` dan `pv_pos`/`pv_neg` (port di kanan) dua-duanya `source`. React Flow mode Strict hanya mengizinkan satu sisi `source` + sisi lain `target`, sehingga port bertipe TUNGGAL tidak punya pasangan yang sah → SEMUA tarikan ditolak di kedua arah, dan itu bukan soal polaritas. Pola yang benar = sepasang handle, sama seperti `DefaultNode` bawaan React Flow; render `target` dulu lalu `source` supaya drag selalu mulai dari source dan berakhir di target (sah di Strict maupun Loose). `connectionMode={ConnectionMode.Loose}` saja **tidak menutup kasus ini** — jangan dijadikan fix utama. Jangan pula memindahkan kutub ke sisi kartu lain demi itu (merusak layout SolarBuilder).
- **Visual kabel + arus (commit `3443ab2`)**: `src/engine/flow.ts` → `edgeCurrents(graph, states)` menghitung arus tiap segmen; `runSim` menyimpannya sebagai `edgeCurrents: number[]` di store **sejajar urutan `edges`** (toEngineGraph memetakan 1:1 tanpa mengubah urutan — kalau urutan itu berubah, panah menunjuk kabel yang salah tanpa error apa pun). Arus panel diambil dari `state.current` modul itu: sejak state diisi per unit, tiap modul punya arus sendiri (seri = arus sama di semua segmen, jadi tidak ada lagi segmen ekor yang mati). JANGAN jatuh ke `imp` STC sebagai cadangan — nilainya tetap 9.51 A walau iradiansi nol, sehingga kabel berpanah palsu di malam hari. Perangkat in-line (fuse/breaker/yConnector/combiner/busbar/disconnect) meneruskan arus; penggabung menjumlahkan. Tanpa hasil sim hasilnya nol semua — jangan menebak dari parameter STC.
- **JEBAKAN: `.react-flow__edge.animated path { stroke-dasharray: 5; animation: dashdraw }`** ada di `@xyflow/react/dist/style.css` dan spesifisitasnya (0,2,1) mengalahkan `.react-flow__edge .cable` (0,2,0) — kabel tebal jadi garis putus-putus bergerak yang menabrak panah arus. Sumbernya `animated: true` pada edge (ada di store mkEdge+onConnect, runSim applyPreset, importSolarBuilder); sudah dibuang di keempatnya + jaring pengaman CSS `.react-flow__edge.animated .cable { stroke-dasharray: none; animation: none }`. Kalau menambah tempat pembuat edge baru, jangan pasang `animated: true`.
- **`<animateMotion>` dari React**: React memunculkan warning dev "`<animateMotion />` is using incorrect casing" (validator JSX), tapi TIDAK merusak apa pun — `react-dom` membuat elemen SVG lewat `createElementNS(namespaceURI, type)` sehingga case terjaga, dan warning tingkat-DOM-nya dijaga `if (namespaceURI === HTML_NAMESPACE)`. Produksi senyap. Pakai `href` DAN `xlinkHref` di `<mpath>`. Verifikasi murah tanpa browser: minta Vite transform modulnya (`curl http://localhost:<port>/src/components/edges/CableEdge.tsx`) lalu cek `jsxDEV("animateMotion"` masih ada.
- **`buildFromBom` (`src/store.ts`) harus merangkai kabel sungguhan**: modul dijadikan string SERI sepanjang `calcs.seriesPerString`, tiap string masuk MPPT pada port PV yang sama (paralel di bus PV), dan bank baterai diseri sesuai tegangan sistem. Tiap node baterai memakai parameter **PER UNIT** (`nominalV`, `capacityWh`, `internalResOhm` satu unit) — kalau diisi nilai seluruh bank, tegangan bank jadi berlipat.
- **Regresi kontrak param UI↔engine:** `tests/capacity-sync.test.tsx` (kartu vs Properties vs `batteryBank`/`batteryStep`) dan `tests/node-cards.test.tsx` (teks kartu unit ke-2) merender komponen lewat `renderToString` — pola termurah untuk membuktikan angka yang dilihat user tanpa browser. ## Kontrak param: UI ↔ engine (satu angka, satu kebenaran)

- **Sebelum mempercayai angka di kartu, cek dulu param yang diedit Properties memang DIBACA engine.** Kelas bug yang berulang: Properties menulis satu field, engine membaca field lain, kartu menghitung sendiri dari field ketiga — tiga angka untuk satu besaran. Cara cepat: `grep -rn "<param>" src/` lalu pisahkan hasilnya jadi penulis (`GroupedProperties`, `paramsFromModel`, `buildFromBom`, import) vs pembaca (`src/engine/**`). Field yang hanya muncul di daftar penulis = field mati; field yang hanya muncul di pembaca = tak bisa diedit user. Untuk baterai: `capacityAh` dulu ditulis Properties tapi dibaca NOL tempat, sementara `capacityWh` dibaca `batteryBank`/`batteryStep` — pilih `capacityWh` sebagai kanonik, dan sediakan `unitCapacityWh()`/`unitCapacityAh()` di `src/engine/array.ts` sebagai SATU helper yang dipakai kartu + Properties + engine. Jangan biarkan dua tempat menghitung besaran turunan yang sama sendiri-sendiri.
- **Satuan tampilan ≠ satuan simpan boleh, asal konversinya di satu tempat.** Field `PropField.asAh` menampilkan kotak isian bersatuan Ah tetapi menyimpan `capacityWh` (Ah × tegangan nominal) dan membaca balik lewat helper yang sama. Kalau menambah field ber-satuan turunan, pakai pola ini — jangan menambah param baru khusus tampilan.
- **Audit param sisa repo — jangan percaya grep mentah, lima file ini menyesatkan.** `src/engine/types.ts` (deklarasi union SEMUA param), `src/store.ts` (`DEFAULT_PARAMS` + spread generik), `src/engine/components.ts` (deskripsi skema), `src/lib/importSolarBuilder.ts` (peta nama impor), dan `src/components/GroupedProperties.tsx` (definisi field itu sendiri) menyebut setiap key. Kalau ikut dihitung, hasilnya "0 param yatim" dan audit berhenti dengan kesimpulan palsu; keluarkan dulu kelimanya, baru cari tiap key sebagai kata utuh (`\\bkey\\b`) di file pemakaian. Pecah hasil jadi tiga kelas, karena hanya kelas ketiga yang berbahaya: MATI (tak dibaca siapa pun), TAMPILAN (dibaca node/Inspector sebagai label), dan TERSEMBUNYI (dibaca engine tapi hasilnya tak pernah muncul di UI). Kelas TERSEMBUNYI yang bikin user salah percaya: angka tampil terlihat final padahal ada faktor yang diabaikan.
- **Hasil audit repo ini (cek ulang sebelum menambah field baru):** MATI — `tempCoeff`, `maxSystemV`, `batteryType`, `maxDischargeAmps`, `controllerType`, `nominalPvWatts`, `absorbTimeHours`, `idleWatts`, `waveType`, `outputVoltsAc`, `frequency`, `fuseType`, `ratingV`, `phases`, `startWatts`, `runMode`, `serviceAmps`, `standard`, `fuel`, `branchCount`. TAMPILAN — `transferAmps`, `powerFactor`, `fuelTank`, `poles`, `rows`. TERSEMBUNYI — `costPerKwh` (tak menyentuh engine/report; RAB cuma harga komponen, jadi penghematan/payback belum punya fondasi), `eff` MPPT (`mpptOutput()` = `min(panelW, battV x maxA)`, tanpa parameter efisiensi), dan kebalikannya `socMin`/`socMax` dibaca `batteryStep` tapi TIDAK punya field UI sehingga DoD AGM tak bisa disetel. Laporan lengkap + tabel rekomendasi: `docs/AUDIT_PARAM.md` di repo.
- **Dua nama untuk satu konsep = salah satunya hampir pasti mati.** Beban punya `startWatts` (field UI, tak dibaca) dan `surgeW` (dibaca `solve.ts` untuk evaluasi surge, tanpa field UI); mengisi Start Watts 2500 W tidak memicu evaluasi surge sama sekali. Saat menambah/mengganti field param, cari dulu sinonimnya di `types.ts` dan `components.ts` sebelum membuat nama baru.
- **Kunci temuan audit dengan tes yang mengunci PERILAKU YANG SALAH**, bukan dengan perbaikan sekaligus. Tulis asersinya dalam bentuk sekarang (mis. `expect(mpptOutput.length).toBe(3)` lalu `expect(pb).toBeCloseTo(pa, 9)` untuk eff 100 vs 80), beri komentar `SAAT INI:` + asersi yang BENAR dalam komentar; begitu nanti diperbaiki, tes merah dan asersinya tinggal dibalik. Ini membuat audit bisa diverifikasi ulang dan tidak menjadi klaim di atas kertas — pola: `tests/audit-params.test.ts`.
- **Normalisasi di `updateNodeParams`, bukan di pemanggil.** Tulisan dari jalur lama (pemilih model, paste props, impor) tetap bisa membawa param usang; terjemahkan ke bentuk kanonik di satu titik (`src/store.ts`) lalu buang alias-nya, supaya komponen lama yang sudah tersimpan tidak bisa memicu desync lagi. Param usang tetap dibaca sebagai CADANGAN lewat helper — jangan dihapus keras, data lama akan mati.
- **Param kapasitas 0 bukan "kosong netral":** `batteryStep` dengan `capacityWh` 0 mengembalikan `{ full: true, empty: true }` sekaligus, sehingga SOC tidak bergerak sama sekali. Kalau user melaporkan "SOC tidak berubah walau ada beban", periksa dulu kapasitas yang benar-benar terbaca engine, bukan rumusnya.
- **`state.soc` saat DISCHARGE berisi SOC BASIS AWAL langkah, bukan hasil akhir** — `solve.ts` sengaja memakai basis `socIn` supaya tegangan terminal dan sag konsisten dengan perhitungan inverter. SOC akhir ada di `out.soc` (`socOut`). Jangan "memperbaiki" ini jadi bug; kalau menulis asersi SOC, bandingkan `out.soc`.

## Audit param Properties vs engine (wajib sebelum menambah field)

- **Pola bug kelas: param yatim.** Field di `PROP_GROUPS` (`GroupedProperties.tsx`) tersimpan dan tampil, tapi tidak dibaca siapa pun. Penyebab paling umum adalah **dua nama untuk satu konsep** (`startWatts` di UI vs `surgeW` di engine) atau **salah satu sisi punya field sedangkan sisi lain tidak** (`socMin`/`socMax` dibaca `batteryStep` tapi tak punya field UI). Hasil audit lengkap 95 field ada di repo: `docs/AUDIT_PARAM.md`.
- **Saat menyisir, JANGAN menghitung 5 file deklarasi sebagai pemakaian**: `src/engine/types.ts` (union semua param), `src/store.ts` (`DEFAULT_PARAMS` + spread), `src/engine/components.ts` (skema), `src/lib/importSolarBuilder.ts` (pemetaan nama), `src/components/GroupedProperties.tsx` (definisi field). Kalau ikut dihitung, SEMUA key tampak terbaca dan audit melaporkan "0 param yatim" — jebakan ini sudah pernah menggagalkan satu putaran audit.
- **Satuan adalah sumber bug tersembunyi.** Properties menyimpan efisiensi & koefisien suhu dalam **persen** (step 1 / 0,01), engine butuh **fraksi**. Heuristik `|x| > 1 ? x/100 : x` SALAH untuk `tempCoeff` (nilai wajar -0,2..-0,5 %/°C = 0,002..0,005 fraksi, jadi -0,29 terbaca sebagai 29 %/°C dan Voc meledak 5x). Pakai ambang 0,05 untuk koefisien suhu; untuk efisiensi/Max SOC ambang 1 aman. Selalu tulis tes yang membandingkan bentuk persen dan fraksi menghasilkan angka identik.
- **Kapasitas baterai: `capacityWh` kanonik, Ah hanya tampilan.** Helper `unitCapacityWh/unitCapacityAh/unitNominalV` di `engine/array.ts` dipakai kartu + Properties + engine sekaligus. Field Capacity di Properties memakai `key: 'capacityWh'` dengan flag `asAh: true`. `capacityAh` tinggal cadangan data lama dan **tidak boleh ditulis** — `store.updateNodeParams` menormalkannya ke Wh.
- **`capacityWh = 0` adalah racun senyap**: `batteryStep` mengembalikan `{full:true, empty:true}` sehingga SOC tidak bergerak sama sekali tanpa error. Kalau SOC terlihat diam, periksa kapasitas bank dulu sebelum menuduh wiring.
- **Nilai tingkat GRUP vs nilai per unit**: `state.power/voltage/current` adalah porsi UNIT, `state.group` membawa total grup. Jangan membaca `states.find(unit)` untuk angka grup — `simulate.ts` pernah begitu dan timeline under-report sebesar jumlah modul. Produksi array diambil dari `out.totalProductionW`.
- **`wireDrops[].from` berisi id TERMINAL (`b1:a`)**, bukan id node — lookup langsung ke peta state selalu meleset (vDrop% selamanya 0). Fixture tes yang memakai `from: 'p1'` menyembunyikan bug ini; selalu salin bentuk asli dari `solve()`.

## Jebakan

- **Nama Victron 100/50 = max 100V INPUT panel / 50A charge ke baterai** — bukan tegangan sistem. Tidak ada produk "24/50". Deteksi 12/24/48V otomatis dari bank.
- **Setel voltase AC ke 230V, bukan 120V** — default simulator bawaan US; Indonesia 220–230V, termasuk beban AC di dalam simulator.
- **AGM hanya jika user setuju kapasitas efektifnya separuh** — DoD AGM 50% vs LiFePO4 80%; 2× AGM 12V 100Ah (2.4 kWh nama) efektif cuma ~1.2 kWh.
- **Warning "DC input undervoltage" di simulator berarti wiring, bukan baterai rusak** — inverter belum terhubung benar ke bus baterai; suruh cek terminal DC+/DC− snap ke bank, bukan ke MPPT.
- Warning "no live AC source" hilang sendiri setelah sambungan inverter–baterai benar; jangan suruh user menelusuri jalur AC.
- Fuse: sisi panel per string 20A, sisi baterai→inverter ~2.5× arus kontinu (24V 1500VA → 60A). Kabel baterai→inverter min 25mm² di 24V.
- **Kalau sesi browser tidak jalan, jangan buang sesi — pindah ke verifikasi offline.** Ambil ground truth dari library yang benar-benar terpasang: `node_modules/@xyflow/system/dist/esm/index.js` (`isValidHandle`, `getClosestHandle`, `connectingSelector` di paket react) dan `node_modules/@xyflow/react/dist/style.css` (geometri handle), lalu harness SSR + tes invariant CSS. Resep lengkap di skill `web-app-runtime-verification` → `references/offline-verification.md`. Ingat batasnya: prop `connectionMode` bertipe, jadi lulus `tsc` = prop sampai ke React Flow — BUKAN bukti perilakunya benar.
- **Jangan menulis asersi tes terhadap string markup yang terlalu umum.** `expect(html).not.toContain('value=""')` gagal karena field LAIN di kartu yang sama memang kosong secara sah (mis. Max Charge); `expect(html).not.toContain('BANK')` bisa kena teks lain. Kunci ke penanda spesifik (`id="grp-capacityWh"`, `data-testid`, potongan baris spek) — asersi lebar membuat tes merah karena alasan yang salah dan menggoda untuk "dilonggarkan" sampai bug aslinya ikut lolos.
- **Asersi angka absolut untuk besaran yang punya efisiensi/sag di dalamnya akan gagal karena alasan tak penting** (SOC turun 0.474 vs 0.260 dari rumus sederhana — discharge `BATT_EFF` + tegangan terminal ikut bermain). Uji secara RELATIF terhadap kasus rusaknya: jalankan solve yang sama dengan param yang menyebabkan bug (mis. `capacityWh` dihapus) lalu pastikan hasil normal bergerak jauh darinya. Itu membuktikan yang diperbaiki tanpa mengunci angka yang akan berubah tiap penyetelan model.
- **Ubah kontrak wiring = grep dulu assertion lama di `tests/`.** Test yang mengunci topologi lama akan merah dan itu BENAR, bukan regresi: `tests/wizard.test.tsx` dulu menegaskan SEMUA panel nyambung langsung ke MPPT, sehingga justru ikut membekukan bug "panel tidak pernah diseri". Perbarui assertion ke bentuk topologi baru — jangan melunakkan kode wiring supaya test lama tetap hijau.
- **Sebelum menyimpulkan "perubahan kapasitas tidak berefek", pastikan dulu batasan mana yang mengikat.** Helper unit uji yang menanam `vmp`/`imp` kecil membuat array dibatasi panel, sehingga menambah MPPT/inverter paralel terlihat nol pengaruh; pakai modul uji yang dayanya jauh di atas batas perangkat yang sedang diuji.
- Dev server Vite bind ke `[::1]` — `curl 127.0.0.1` gagal (000), pakai `localhost`. Mematikannya: PID dari `netstat -ano | grep <port>`, lalu `powershell -NoProfile -Command "Stop-Process -Id <pid> -Force"`; `taskkill //PID` tidak jalan di bash MSYS.
- **`patch` bisa menolak match di file CRLF repo ini** (blok pendek + baris campuran). Untuk edit persis, pakai `execute_code` Python: `io.open(p, 'r', encoding='utf-8', newline='')`, `src.replace(old, new)` dengan `\r\n` eksplisit, `assert src.count(old) == 1` SEBELUM menulis, tulis balik dengan `newline=''` supaya line ending tidak berubah. Kalau tetap pakai `patch`, sertakan blok lebih panjang sebagai konteks (blok 2-3 baris sering gagal, blok 10 baris lolos).

## Catatan alat
- Solar Builder tidak perlu dibuka user lagi saat fase paritas UI: bundle Vite-nya (JS + CSS) dan HTML shell 1–2 KB bisa di-`curl`, DOM live dibaca lewat puppeteer-core headless. Ambil **CSS dulu** (semua token warna/ukuran ada di sana), DOM belakangan. Kalau tool browser bawaan menolak karena profil Edge user terkunci, jangan bilang situsnya berat — pakai puppeteer + `userDataDir` sendiri di scratch.
- Ekspor diagram Solar Builder adalah `.svg` (mis. Downloads/SolarBuilder-Diagram.svg). Untuk analisis VISUAL (warna kartu, styling kabel, layout), rasterize dulu pakai headless Edge lalu vision_analyze PNG-nya: `msedge.exe --headless=new --disable-gpu --window-size=1600,600 --screenshot=out.png file:///...svg`. Fallback text-only tanpa render: regex text node (`re.findall(r'<text[^>]*>(.*?)</text>', s)`; tspan bersarang ikut tertangkap) — cukup untuk label komponen + rating.
- Sertakan penjelasan konsep saat user bertanya (seri vs paralel, arti angka MPPT) — jawab singkat berbahasa Indonesia dengan tabel/diagram ascii kecil.
- Sesi belajar/latihan sizing: ajari DULU alasan di balik tiap rumus (kenapa rugi 0.8 di penyebut, arah pengali) baru berikan soal studi kasus — jangan langsung bom soal. Soal berjenjang dengan jebakan nyata (DoD AGM, Voc dingin, surge motor); kunci jawaban selalu dihitung via execute_code terlebih dahulu; saat cek jawaban user, tunjukkan cek arah hasil (kondisi lebih jelek harus butuh panel lebih BESAR, bukan kecil) sebagai alat deteksi kesalahan sendiri.
- Ekstraksi SVG Solar Builder untuk model PORT/struktur: ambil `<text x= y=>` berpasangan posisi+isi dan `<circle r="5">` sebagai titik port; tabel hasil distill ada di `references/solarbuilder-ui.md` § model port.
